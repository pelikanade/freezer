# Deployment is one container, not a NixOS module

Freezer is deployed as a single container run by rootless Podman on a plain Linux host: the `Dockerfile` in the repository root, and the Quadlet unit plus example configuration in `deploy/`. The flake keeps `packages.<system>.default` for the Nix route and for self-hosting, but no longer exports `nixosModules.default`, and `nix/module.nix` is gone. The image compiles the Go package with the official Go toolchain image and runs the result on the official Nix image.

The module required a NixOS host and reached the host's Nix daemon, and it spread the service's runtime shape across the host's configuration: a service account, a state directory, an environment file, and the process hardening of a systemd unit. The container puts all of that in one image. The official Nix image already carries Nix 2.34.8, git, tar and curl, so the deployment host needs no Nix and no service account: the container's root is a mapped unprivileged user, and everything Freezer writes lives under that user's home.

## Consequences

- Nix moves into the container. ADR 0010 and ADR 0017 are unchanged in substance — Nix still does every build, probe and copy, and still fails loudly rather than validating anything up front — but the version floor is now satisfied by construction: the image pins 2.34.8, and a hand-built image is on its own.
- The local store is the container's writable layer. It survives stop, start and reboot of the same container, and is discarded when the container is recreated (a new image tag, or an edited unit). Because R2 holds the published paths, a discarded store costs rebuild time on the next push and never re-publication; `state_dir` is a bind mount and does survive recreation.
- The configuration file, the environment file and the signing key are mounts, so the same three paths exist in every deployment, and the `listen` address in the config is the container's `0.0.0.0:8080` rather than a loopback bind.
- The service is a *user* service: it starts at boot because the unit is wanted by `default.target` and lingering is enabled, not because a system-level unit exists. Stopping, inspecting and upgrading it are `systemctl --user` operations.
- The image sets `sandbox = true` with `sandbox-fallback = false`: builds are sandboxed, and a runtime that cannot give the container root the needed namespaces fails each build with Nix's own error instead of quietly building without a sandbox. The escape hatch is a `nix.conf` mounted with `sandbox = false`, and it removes the sandbox from the trust story, because a build then sees the container's environment with the R2 credentials and the GitHub token in it.
- `build-users-group` is empty and the store is single-user, so the deployment depends on no subuid range beyond the one rootless Podman itself needs, and no build user has to be mapped. The sandbox, not a build account, is what confines a build.
- Building the image runs no Nix. Compiling in the runtime image with `RUN nix build .#default` was tried and dropped on evidence: with `sandbox = false` the non-chroot builder requires `/homeless-shelter` — the `HOME` Nix hands to builders — to be absent for *every* derivation, and a builder that writes into it (the Go module fetcher does) makes every later build in that container fail with "home directory /homeless-shelter exists"; with `sandbox = true` the build needs a user namespace, which rootful Docker does not give `docker build`. A Go stage has neither problem, and Nix's presence in the image is for building the *registered repositories*, not for building Freezer.

## Considered Options

- **Keeping both routes.** Rejected: two deployment paths that differ in behaviour — the host's daemon versus the container's Nix — would each need to be documented, tested and kept honest, for a service one person runs on one host.
- **Building the image with `dockerTools.buildLayeredImage`.** Rejected: it makes Nix a prerequisite of the machine that builds the image. A Dockerfile needs only Podman or Docker, a network and the base image.
- **Installing Nix into a distribution base image by hand.** Rejected: the official image is built for exactly this use, and inspecting it confirmed Nix, git (with `git-remote-https`), tar, curl and a CA bundle are already on `PATH`.
- **A host directory or named volume mounted at `/nix`.** Rejected as the default: it hides the image's own `/nix` — the Nix and git binaries live under `/nix/store` — so the volume has to be seeded from the image first, and a later re-seed would overwrite the store database and strand the paths built inside the container. The container's writable layer has no such failure mode, and the store is a cache whose durable copy is R2.
- **Compiling Freezer with Nix inside the runtime image** (`RUN nix build .#default` on the Nix base). Rejected on evidence, as above: unsandboxed it breaks on the first build whose predecessor wrote to its `HOME`, and sandboxed it needs a user namespace that `docker build` does not provide. The Nix floor and the store belong to the running service, not to the image build.
